# 项目答辩可能问题与回答

> 适用场景：课程实践、项目验收、答辩问询。回答口径应客观，不把演示结果夸大为生产级系统能力。

## 一、项目整体介绍

### 1. 这个项目主要做了什么？

本项目实现了一个基于 CICIDS2017 的网络入侵检测与安全运营平台。整体流程包括数据清洗、特征分析、模型训练对比、实时检测服务和前端告警展示。系统使用 XGBoost 多分类模型识别 BENIGN、DDoS、DoS、PortScan、Botnet、BruteForce、WebAttack、Infiltration 等 8 类流量，并结合行为规则补充端口扫描、SYN 洪泛等跨流攻击识别。

### 2. 项目的完整技术链路是什么？

离线部分是：CICIDS2017 原始 CSV 数据 -> 数据清洗 -> 标签归并 -> 特征分析 -> 训练 RandomForest、XGBoost、CNN-LSTM、Transformer -> 指标对比 -> 保存最优模型。

在线部分分两条入口：pcap 回放或 Scapy 实时抓包 -> 双向五元组流聚合 -> 生成 69 维 CICIDS 风格特征 -> XGBoost 推理及行为规则检测；模拟模式则直接从特征样本池抽样后调用模型。两条入口最终复用事件构建、SQLite 存储和前端展示流程。

### 3. 项目实现了哪些功能？

- CICIDS2017 数据清洗与标签映射。
- RandomForest、XGBoost、CNN-LSTM、Transformer 模型训练与对比。
- XGBoost 多分类入侵检测。
- FastAPI 推理接口、事件流接口和告警管理接口。
- Vue + ECharts 实时监控面板。
- 模拟流量、pcap 回放、实时抓包三种输入方式。
- 告警列表、风险等级、置信度、源/目标 IP、状态流转。
- SHAP 特征解释与历史解释缓存。
- SQLite 告警持久化和 CSV 导出。
- Docker 一键部署。

## 二、项目创新点与答辩口径

### 创新点 1：单流模型与跨流行为规则互补

XGBoost 对单条网络流做 8 分类，端口扫描和 SYN 洪泛检测器则聚合多条流的行为。例如扫描产生的单条短连接信息有限，把同一源 IP 访问的不同目标端口累计起来，才更容易发现异常。

实现位置：[`_capture_emit`](../detector/api_server.py) 将模型结果与 [`PortScanDetector`、`SynFloodDetector`](../detector/flow_extractor.py) 的命中结果写入事件链路。

**答辩可说：**“我的应用改进是把单流统计分类和跨流行为识别结合起来，覆盖两种不同粒度的检测需求。”

**能力边界：**当前是并行产生告警，没有学习型融合模型，也没有完成模型单独、规则单独、组合方案的消融对比。因此可以说补充了检测路径，不能声称已经证明准确率提高了多少。

### 创新点 2：把模型解释接入告警复核流程

系统将攻击类别、置信度、流量特征、SHAP Top-5 贡献、规则证据和处置建议放在告警详情中，并提供确认、忽略、关闭等状态操作。这样分析者可以结合特征贡献复核模型判断，保存的解释也能随历史告警查看。

实现位置：[`explain`](../detector/explain.py)、[`explain_by_id`](../detector/api_server.py)、[`update_shap`](../detector/db.py) 和 [`前端详情面板`](../detector/static/index.html)。

**答辩可说：**“我把可解释性做成了告警工作流的一部分，让模型输出能被查看和复核。”

**能力边界：**SHAP 是已有方法，本项目的贡献在于应用接入。SHAP 解释模型输出，不能解释跨流规则的触发逻辑，也不能证明攻击确实发生。

### 创新点 3：提供分层验证入口和可重复演示流程

特征模拟用于检查推理和页面交互，pcap 回放用于重复检查包解析与流特征提取，实时抓包用于观察所选网卡可见的实际流量。三种模式便于分别定位模型、特征提取和采集环境中的问题。“清空模拟事件”提供演示数据清理，减少前后两轮观察相互干扰。

实现位置：[`simulate.py`](../detector/simulate.py)、[`replay_pcap`、`sniff_loop`](../detector/flow_extractor.py)、[`simulate_clear`](../detector/api_server.py)。

**答辩可说：**“我设计了从特征级演示、包级复现到网卡采集的分层验证方式，并复用了后续告警处理流程。”

**能力边界：**模拟不发送真实网络包，回放也不把包重新发到网卡。目前回放和实时抓包均使用 `capture` 来源标签，尚未做到独立会话编号和三类来源的完整隔离。

### 创新点 4：完成从离线实验到在线检测原型的工程整合

项目把数据清洗、模型对比、模型及特征元信息保存、FastAPI 推理、SSE 推送、SQLite 持久化和 Vue 面板串联起来。模型选型结合已有实验结果、表格特征输入形态和解释需求，最终将 XGBoost 接入在线服务。

**答辩可说：**“这个实践的主要价值是完成一套可运行、可解释、可复现的检测原型，并明确离线指标与实际网络效果之间的差距。”

**能力边界：**这些属于课程项目的工程特色和应用整合，不是新的机器学习算法，也不能直接等同于成熟安全产品的生产能力。

### 老师追问：是不是只是把现有工具拼起来？

回答：底层算法和框架确实采用现有工具。我的实现工作主要是特征输入对齐、双向流聚合、跨流规则接入、解释结果与告警关联，以及实时展示和历史存储。课程实践可以体现工程设计与实现能力；若要进一步形成研究创新，需要提出可检验的新方法，并用基线对比、消融实验和真实流量评估证明收益。

### 创新点 30 秒口述版

本项目的创新主要体现在应用和工程实现上。第一，用单流 XGBoost 分类配合跨流行为规则，补充不同粒度的检测能力；第二，把 SHAP 解释接入告警详情与人工复核流程；第三，提供特征模拟、pcap 回放和实时抓包的分层验证入口。最终完成从离线模型到在线告警平台的整合。目前还需要用消融实验和真实流量标注评估这些设计的实际收益。

## 三、数据与预处理

### 4. 为什么选择 CICIDS2017？

CICIDS2017 是入侵检测领域常用公开数据集，包含正常流量和多类攻击流量，数据规模较大，且已经提供流量统计特征，适合做传统机器学习和深度学习模型对比。它覆盖 DDoS、DoS、PortScan、WebAttack、Botnet 等典型攻击类型，能支撑多分类异常检测实验。

### 5. 数据清洗做了哪些工作？

主要包括列名规范化、非法值处理、缺失值处理、常量列删除、标签归并和数值特征筛选。CICIDS2017 原始文件中存在列名空格、`Inf`、`-Inf`、异常字符和跨文件列不一致等问题，如果不清洗，会影响模型训练和特征对齐。

### 6. 为什么把原始标签归并为 8 类？

原始标签中有些攻击子类样本极少，直接做细粒度多分类会导致类别严重不平衡，模型很难学到稳定边界。因此项目将相近攻击合并为 8 大类，在保留主要攻击语义的同时降低建模难度，也更符合实践系统中的威胁类别展示。

### 7. 类别不平衡问题怎么处理？

机器学习模型中使用了类别权重或样本权重，例如 RandomForest 的 `class_weight` 和 XGBoost 的逆频样本权重。深度学习模型也使用逆频类别权重。这样可以提高少数类在训练损失中的影响，但也会带来误报升高的问题，所以报告中同时关注 Macro-F1、Weighted-F1 和各类别表现。

## 四、模型选择与实验

### 8. 为什么最终选择 XGBoost？

因为 CICIDS2017 的输入是 69 维手工设计的表格特征，而 XGBoost 对表格数据非常适合，能通过树分裂捕获非线性特征交互。实验中 XGBoost 在二分类和多分类上都取得最好结果，并且训练速度快、推理稳定、便于接入 SHAP 做可解释分析。

### 9. 为什么 Transformer 效果不如 XGBoost？

项目中的 Transformer 是把 69 维表格特征补零成 128 长度的伪序列，这种输入没有真实时间顺序或语义位置关系。Transformer 更适合文本、语音、原始时序等有序数据。当前结果说明在这个表格特征场景下，树模型先验更匹配。需要注意的是，当前深度学习结果应视为探索性基线，不能简单说“Transformer 一定不行”。

### 10. Transformer 训练步数少，会不会不严谨？

这是一个合理质疑。原始实验中 Transformer 只训练 10 epoch，loss 仍在下降，因此不应把它当作充分调优结果。项目已把训练脚本调整为最多 50 epoch、验证集早停、最佳权重回滚和 AdamW 正则。答辩时应说明：当前表格中 DL 指标是探索性基线，严谨结论是“在当前训练预算与表格特征设定下，XGBoost 明显更优”。

### 11. 为什么不用深度学习作为最终模型？

深度学习不是不能用，而是在本项目的数据形态下性价比不高。当前输入已经是专家设计过的统计特征，不是原始包序列或字节流。树模型能更直接地利用这些异构数值特征，训练更快、效果更好、解释也更方便。深度学习更适合作为后续扩展，例如使用原始流量序列、包序列或更大规模数据训练。

### 12. 评估指标为什么要看 Macro-F1？

因为数据类别不平衡严重，Weighted-F1 容易被 BENIGN 和大样本攻击类主导。Macro-F1 对每个类别一视同仁，更能反映少数类检测效果。因此多分类任务中不能只看 Accuracy 或 Weighted-F1，还要看 Macro-F1 和单类 F1。

## 五、实时检测实现

### 13. 实时抓包是怎么实现的？

系统使用 Scapy 从网卡抓取真实数据包，然后按五元组聚合为网络流。每条流在超时后被结算，提取 CICIDS 风格的 69 维统计特征，再送入 XGBoost 模型预测。前端可以启动或停止抓包，并显示包数、流数和告警数。

### 14. pcap 回放和模拟流量有什么区别？

模拟流量是从已有特征样本中抽取并加噪声，用来快速演示模型推理和告警展示。pcap 回放是读取真实或合成的抓包文件，走“包解析 -> 流聚合 -> 特征提取 -> 模型检测”的完整链路。pcap 回放比模拟流量更接近真实部署，但仍不等同于长期真实网络运行。

### 15. 为什么正常流量不全部显示？

抓包和回放路径只把模型判定为异常或行为规则命中的流量写入告警列表，正常流仍参与统计。模拟路径目前会把包括 BENIGN 在内的预测结果都写成事件，因此不能笼统说所有模式都过滤了正常流量。

### 16. 行为启发式规则有什么作用？

机器学习模型基于单条流特征预测，但端口扫描、SYN 洪泛等攻击有时需要跨流聚合才能识别。例如端口扫描表现为同一源 IP 在短时间内访问多个端口，单条流本身可能特征很弱。因此系统加入端口扫描和 SYN 洪泛规则，与 XGBoost 形成互补。

### 17. 实时抓包为什么需要 Npcap 和管理员权限？

Windows 下普通应用默认没有底层网卡抓包权限，Scapy 依赖 Npcap/WinPcap 兼容接口读取链路层数据。因此需要安装 Npcap，并以管理员权限运行后端服务。这是系统环境限制，不是模型问题。

## 六、前端与工程实现

### 18. 前端实现了哪些交互？

前端实现了实时事件列表、统计卡片、攻击类型图表、风险筛选、时间筛选、排序、告警详情抽屉、状态流转、SHAP Top-5 解释、完整原始特征查看、CSV 导出、模拟控制、pcap 回放和实时抓包控制。

### 19. 后端主要接口有哪些？

核心接口包括 `/predict` 模型推理、`/events` SSE 实时事件流、`/alerts` 历史告警查询、`/explain/{event_id}` SHAP 解释、`/simulate/start` 和 `/simulate/stop` 模拟流量控制、`/simulate/clear` 清空模拟事件、`/capture/start` 和 `/capture/stop` 实时抓包控制、`/capture/replay` pcap 回放。

### 20. 为什么使用 SSE 而不是 WebSocket？

当前系统主要是后端向前端单向推送告警事件，交互复杂度不高。SSE 实现简单，浏览器原生支持，适合实时告警流。如果后续需要双向控制、多人协作或高频交互，可以替换为 WebSocket。

### 21. SQLite 是否足够？

对课程项目和单机演示来说 SQLite 足够，部署简单、无需额外数据库服务，并能持久化告警、状态和 SHAP 缓存。但生产环境中如果有高并发写入、多用户查询和长期归档，应迁移到 PostgreSQL、ClickHouse 或 Elasticsearch 等更适合日志和安全事件分析的存储。

## 七、可解释性

### 22. SHAP 在项目中起什么作用？

SHAP 用于解释 XGBoost 的预测结果。它把模型输出拆解为各个特征对当前预测的贡献，前端展示 Top-5 影响特征和贡献方向。这样安全分析人员不仅能看到“模型判定为 DoS”，还能看到模型主要依据哪些流量特征做出判断。

### 23. SHAP 能证明模型一定正确吗？

不能。SHAP 解释的是模型内部决策依据，不是真实因果证明。它能帮助分析人员判断模型是否依据合理特征，但不能替代人工复核和真实攻击证据。答辩时应表述为“提高可解释性和可核查性”，不要说成“证明检测结果正确”。

### 24. 为什么要缓存 SHAP 结果？

系统在解释计算成功后将结果写入 SQLite，前端打开含 `shap_result` 的历史事件时可直接读取。原始特征仅在内存保留最近 200 条；没有保存过解释且特征已过期的事件，不能重新计算解释。当前按 ID 解释接口本身也没有优先读取数据库缓存，因此不能声称所有解释请求都会命中缓存。

## 八、项目不足与改进

### 25. 当前项目有哪些不足？

- 数据集较旧，不能完全代表最新攻击手法。
- 实时特征提取是对 CICIDS 特征的近似实现，与官方 CICFlowMeter 可能存在偏差。
- 深度学习模型仍是探索性基线，尚未做充分超参搜索。
- 少数类样本极少，例如 Infiltration，很难稳定学习。
- 当前系统更偏单机演示，缺少多用户权限、审计日志和生产级告警闭环。
- 模型没有在线学习能力，无法自动适应新型攻击。
- 实时抓包依赖 Npcap 和管理员权限，部署门槛较高。

### 26. 如果继续改进，你会怎么做？

首先会增强数据和评估，用全量数据、更多真实 pcap 和跨时间验证集评估泛化能力。其次会改进特征提取，接入 CICFlowMeter、Zeek 或 Suricata 以提高特征一致性。第三会对深度学习模型做更充分训练、早停、阈值校准和超参搜索。工程上会引入用户权限、告警工单、日志检索、规则配置和更可靠的数据库。

### 27. 这个系统能直接用于生产吗？

不能直接用于生产。它已经具备原型系统能力，包括模型检测、实时面板、告警管理和解释功能，但生产环境还需要更严格的特征对齐、长期流量验证、误报控制、性能压测、权限管理、日志留存、模型更新机制和安全加固。

### 28. 当前模型对未知攻击有没有检测能力？

模型对训练分布内相似攻击有一定泛化能力，但对完全未知攻击不能保证准确识别。系统通过行为启发式规则补充部分模型盲区，例如 SYN 洪泛和端口扫描。后续可以加入异常检测、自监督流量表征学习或规则库联动，提升未知攻击发现能力。

## 九、老师可能追问与推荐回答

### 29. 老师问：你这个“实时抓包”是真实流量还是模拟？

回答：系统支持三种来源。模拟流量用于快速演示，pcap 回放用于离线复现抓包文件，实时抓包则使用 Scapy 从本机网卡读取真实包。真实抓包在 Windows 下需要 Npcap 和管理员权限。抓到的包会经过五元组聚合、特征提取、模型推理和告警展示。

### 30. 老师问：你怎么保证实时特征和训练特征一致？

回答：目前保证了特征名称和模型输入顺序对齐，并已将 Flow Duration、IAT 和 active/idle 时长统一为微秒。但包长、header length、subflow 和 active/idle 分段仍有近似实现。下一步应选取同一份 pcap，与训练数据所用提取器逐列比较单位、方向和数值，再验证模型。仅替换成 Zeek 等工具也不会自动实现 69 个特征的一一对应。

### 31. 老师问：为什么 Accuracy 很高但 Macro-F1 没那么高？

回答：因为数据类别极不平衡。BENIGN 和 DoS、DDoS 等大类样本多，模型在这些类上表现好会拉高 Accuracy 和 Weighted-F1。但 Infiltration、Botnet 等少数类样本很少，单类 F1 较低，会拉低 Macro-F1。因此多分类评估必须看 Macro-F1 和单类指标。

### 32. 老师问：为什么不直接用规则检测？

回答：规则检测对已知模式有效，但维护成本高，对变种攻击和复杂流量泛化不足。模型可以从统计特征中学习更复杂的边界。项目没有完全抛弃规则，而是采用“模型 + 行为启发式”互补：模型负责分布内多分类，规则补足跨流行为特征明显的攻击。

### 33. 老师问：为什么不用深度学习端到端处理原始包？

回答：这是后续值得做的方向，但本项目优先基于 CICIDS2017 的流统计特征实现完整平台。原始包端到端学习需要更大数据量、更高计算资源和更复杂的数据标注，同时解释性和部署稳定性也更难。当前阶段选择 XGBoost 是基于数据形态、效果、可解释性和工程落地的综合权衡。

### 34. 老师问：SHAP 为什么适合这个项目？

回答：因为最终模型是 XGBoost 树模型，SHAP 对树模型有成熟的 TreeExplainer，可以较高效地计算特征贡献。安全告警场景需要可解释性，SHAP 能把黑盒预测转化为可读证据，帮助判断告警是否合理。

### 35. 老师问：你项目中最有价值的工程点是什么？

回答：不是单纯训练了一个模型，而是把模型接入了可运行的检测平台。系统实现了数据处理、模型推理、实时事件流、告警持久化、状态管理、SHAP 解释、pcap 回放和实时抓包入口，形成了从离线实验到在线演示的完整闭环。

### 36. 老师问：如果现场演示没有真实攻击流量怎么办？

回答：可以使用两种方式演示。第一是模拟流量，它从特征池中抽样并走真实模型推理，适合快速展示告警面板。第二是 pcap 回放，它读取项目自带或外部 pcap 文件，走完整的包解析和流特征提取链路。真实抓包需要系统权限和网卡环境，现场不稳定时不强依赖它。

### 37. 老师问：模型误报怎么办？

回答：系统通过置信度、风险等级、SHAP 解释和告警状态管理帮助人工复核。后续可以做阈值校准、白名单、规则抑制、时间窗口聚合和反馈学习，降低误报率。安全系统中完全消除误报很难，关键是让误报可解释、可过滤、可闭环处理。

### 38. 老师问：项目中你遇到的主要困难是什么？

回答：主要有三类。第一是数据清洗，CICIDS2017 存在列名、非法值、类别不平衡等问题。第二是模型选择，深度学习在表格特征上并不天然占优，需要客观分析。第三是工程接入，把离线模型变成可实时推理、可展示、可解释的系统，需要处理特征对齐、事件流、持久化和前端交互。

### 39. 老师问：这个项目和普通机器学习分类实验有什么区别？

回答：普通分类实验通常停留在训练和测试指标。本项目进一步做了实时服务化和安全运营展示：模型通过 FastAPI 暴露推理接口，前端实时展示告警，支持告警状态、风险筛选、SHAP 解释、历史持久化、pcap 回放和实时抓包，因此更接近一个可交付的安全检测原型。

### 40. 老师问：你怎么防止下次模拟和上次模拟混淆？

回答：前端提供了“清空模拟事件”按钮，后端 `/simulate/clear` 会清除内存中来源为 `simulate` 的事件，并删除 SQLite 中对应历史记录。这样每次演示前可以先清空模拟告警，避免新旧事件混在一起影响观察。

## 十、具体技术细节与深入追问

> 以下参数和限制按当前源码整理；实际训练轮数和实验成绩应以对应运行日志与结果文件为准。

### 41. 五元组是什么？如何把请求和响应合成同一条流？

回答：五元组包括源 IP、目标 IP、源端口、目标端口和协议。`FlowExtractor.process` 同时检查正向键与交换源目标后的反向键。首个观测到的包确定正向，反向包计入同一条流的后向统计。例如 `A:50000 -> B:443/TCP` 与 `B:443 -> A:50000/TCP` 会合并。抓包从连接中途开始时，首包方向不一定等于真正的客户端方向。

代码位置：[`FlowExtractor.process`](../detector/flow_extractor.py)。

### 42. 收到一个包就马上预测吗？“实时”的延迟是多少？

回答：当前先聚合流，再在流空闲超时后预测。接口默认空闲超时为 15 秒，抓包循环用约 1 秒的超时返回来检查过期流，停止时会结算剩余流；因此不能说检测延迟就是模型推理耗时。总延迟包含流等待、提取、推理、存储和页面推送。持续活跃的长连接可能一直不结算，后续需要最大流时长或周期性窗口检测。

代码位置：[`capture_start`](../detector/api_server.py)、[`sniff_loop`、`FlowExtractor.expire`](../detector/flow_extractor.py)。

### 43. 69 个特征怎样保证顺序不乱？缺失值怎么办？

回答：加载模型时同时读取 `ids_xgb_multi.meta.json` 中的 `feature_cols` 和 `class_names`。字典输入会先规范化列名，再按 `feature_cols` 填入向量，不能依赖请求中键的排列顺序。列表输入则要求长度相同，由调用方保证顺序。字典缺失项和无法转换为数值的项当前按 0 处理。

追问回答：补 0 只是一种容错，不代表该统计量真的等于 0；当前也没有完整的非有限数值、特征范围和缺失比例校验。正式部署应对关键特征缺失给出质量提示或拒绝推理，并检查单位与统计口径。

代码位置：[`load_model`、`_to_row`、`predict`](../detector/inference.py)。

### 44. 端口扫描规则的具体阈值是什么？会不会误报？

回答：当前只处理 TCP 元数据，按源 IP 记录最近 30 秒出现的不同目标端口，超过 15 个，也就是至少 16 个端口时触发；触发后清空该源的端口记录。它没有按目标 IP 分组，所以同一源访问多个目标的不同端口也会累计。正常运维扫描和多服务访问可能触发，需要结合授权扫描清单与业务背景复核。

代码位置：[`PortScanDetector.feed`](../detector/flow_extractor.py)。

### 45. SYN 洪泛规则怎样跨流统计？10 秒窗口按什么时间算？

回答：规则按“源 IP、目标 IP、目标端口”聚合，累计带 SYN 且没有反向包的到期流。10 秒窗口内累计 SYN 超过 100 个时触发 DoS 告警，并设置 10 秒冷却期。这是当前原型中的启发式条件，不是经过校准的通用阈值。

追问回答：当前已通过共享的 `DetectionEngine` 将流的 `end_ts` 传给规则，过期流按结束时间排序，避免使用机器处理时钟影响回放结果。它仍是在流结算后统计，流内较早的 SYN 会归入流结束时间，因此不能等同于严格的逐包滑动窗口。多源分散攻击和低速攻击也可能漏检。

代码位置：[`SynFloodDetector.feed`](../detector/flow_extractor.py)、[`_capture_emit`](../detector/api_server.py)。

### 46. 模型和规则判断不同怎么办？置信度 0.92 是怎么算的？

回答：目前模型异常结果和规则命中各自生成事件，没有统一裁决或自动去重；同一批流量可能产生多条相关告警。模型置信度取最高类别输出概率，端口扫描的 0.92 和 SYN 洪泛的 0.93 则是代码设置的固定展示值，不能解释成经过验证的攻击发生概率。风险等级另外按攻击类别映射，也不是置信度换算。

后续改进：分别展示模型分数与规则命中依据，用关联 ID 聚合同一事件，再通过标注数据做阈值或概率校准。

代码位置：[`_capture_emit`、`_make_event`](../detector/api_server.py)、[`predict`](../detector/inference.py)。

### 47. Transformer 的输入维度和网络结构是什么？

回答：多分类脚本将标准化后的 69 维特征补零为 `[批大小, 128, 1]`，通过线性层映射到 64 维，加入可学习的位置嵌入，再进入 2 层、8 个注意力头的 Transformer Encoder。前馈层维度为 256，dropout 为 0.1，最后沿 128 个位置平均池化，线性层输出 8 类分数。

追问回答：这些位置对应统计特征和补零项，不是真实的包时间序列。目前也没有给补零位置设置注意力掩码，补零项会经过投影和位置嵌入参与计算。因此不能把当前实验说成已经验证了 Transformer 对原始网络时序的建模能力。

代码位置：[`to_sequence`、`TransformerModel`](../src/train_dl_multi.py)。

### 48. epoch、batch 和 step 有什么区别？现在到底训练了多少步？

回答：batch 是一次处理的一组样本，训练 step 通常指一次梯度更新，epoch 是完整遍历一轮训练集。当前多分类脚本抽样 30 万条，先划出 20% 测试集，再从剩余部分划出 10% 验证集，训练集约 21.6 万条；batch size 为 1024，未丢弃末批时每轮约 `ceil(216000 / 1024) = 211` 个更新步骤。

最多 50 epoch 对应约 10550 个更新步骤，但早停可能提前结束。当前配置为 AdamW、学习率 `1e-3`、权重衰减 `1e-4`，验证损失连续 8 轮未达到 `1e-4` 的改善量时早停，并恢复最佳权重。配置上限不等于已经训练完成，实际轮数应查看 `best_epoch`、训练日志和相应结果文件。

代码位置：[`训练配置与训练循环`](../src/train_dl_multi.py)。

### 49. 验证集和测试集怎么分工？现有划分够严谨吗？

回答：训练集更新参数，验证集选择最佳轮数，测试集用于最终评价。当前脚本分层随机划分，能保持类别比例，但不能证明跨日期、跨主机的泛化能力。同一会话或高度相似流可能落入不同集合，应补充按时间、主机或会话分组的评估。

还有一个实现细节：当前 DL 脚本先在 80% 数据上拟合标准化器，再从这部分划出验证集，因此标准化统计量包含了后来验证集的信息。测试集没有参与标准化拟合，但验证流程还应改为先完成三份划分，再只在最终训练集上拟合预处理器。修改之后需要重新训练和更新结果。

代码位置：[`split_standardize` 和主训练流程](../src/train_dl_multi.py)。

### 50. SSE 怎样推送？断线后能保证不漏告警吗？

回答：前端用 `EventSource('/events')` 接收事件，后端 `StreamingResponse` 返回 `text/event-stream`，每 0.5 秒检查一次内存事件列表并发送新增项。当前没有实现带事件序号的断点续传和可靠消息确认。

现有边界：内存最多保留 500 条事件，推送游标却按列表长度记录；列表满后长度不再增长，新事件可能不能继续推送。因此目前不能保证长期运行不漏推送。后续需要使用单调事件序号或消息队列，并通过历史查询补齐，而不能把数据库持久化等同于前端可靠送达。

代码位置：[`_emit_event`、`events_stream`](../detector/api_server.py)。

### 51. SHAP Top-5 的占比和正负号分别代表什么？

回答：代码先取模型预测类别对应的 SHAP 贡献，按绝对值排序取前 5 个。正值表示推动该类别的模型输出，负值表示抑制该输出。占比计算为 `abs(某特征贡献) / 所有特征贡献绝对值之和 * 100%`，因此 Top-5 的占比不一定相加为 100%，也不是“攻击概率占比”。

追问回答：解释模块目前使用了修改 SHAP 内部加载逻辑的 `base_score` 兼容补丁，需要进一步验证解释基线和贡献重构是否正确。规则告警应看规则证据，不能用另一条模型解释替代规则原因。

代码位置：[`explain`、`_patch_ubjson_base_score`](../detector/explain.py)。

### 52. 清空模拟事件具体删什么？为什么清空后还可能出现事件？

回答：`/simulate/clear` 按来源删除内存事件中的 `simulate` 记录、这些事件对应的特征缓存，以及 SQLite 中 `source = 'simulate'` 的记录。它不删除训练数据、模型、pcap 文件或抓包来源告警，也不重建模拟特征池。

清空接口不会停止模拟线程，继续运行的线程仍能生成新事件。演示时应先停止模拟，再清空，再开始下一轮。当前没有按模拟会话编号隔离，也没有把内存清理与数据库删除做成一个整体原子操作；页面提示“后端未同步”时不能说历史数据已经删除成功。

代码位置：[`simulate_clear`](../detector/api_server.py)、[`clearSimEvents`](../detector/static/index.html)。

### 53. 模拟告警能拿来证明准确率吗？页面上的 IP 是真实的吗？

回答：不能。模拟器从清洗后的数据中每类最多取 60 条样本，设置约 30% 正常、70% 攻击的演示采样权重，再给特征增加少量噪声并调用真实模型。显示的源目标 IP 从预设列表随机选取，端口也是按类别生成的展示元数据，并非当前电脑的连接证据。

模拟池没有与训练集明确隔离，加噪特征也不保证满足真实协议和统计约束，所以它用于功能演示，不用于计算独立测试性能或真实攻击发生率。

代码位置：[`build_pool`、`next_event`、`_make_meta`](../detector/simulate.py)。

### 54. 本机抓包能看到整个局域网吗？能读取 HTTPS 内容吗？

回答：当前程序监听所选网卡能交付给它的数据包，不能由此声称能看到整个局域网。代码提取的是地址、端口、包长、时间间隔和 TCP 标志等统计信息，没有实现 TLS 解密，也没有应用层攻击内容解析。即使模型输出 WebAttack，也只是统计特征分类结果，需要额外证据才能确认具体攻击行为。

代码位置：[`sniff_loop`、`Flow.add`、`Flow.to_features`](../detector/flow_extractor.py)。

### 55. 如何证明创新点有用？答辩之后优先补什么实验？

回答：优先做模型单独、规则单独、模型与规则组合的消融对比，使用相同的独立标注流量和时间范围，比较各攻击类 Precision、Recall、F1、正常流量误报率以及重复告警数。正常连接应作为负样本纳入评估，不能只播放攻击样本看是否产生告警。

工程部分还应记录包接收量、流结算量、从包到页面的延迟、资源占用和长时间推送完整性。解释部分应检查高贡献特征是否合理，以及基线加贡献能否重构对应模型输出。真实流量没有标签时，只能报告运行现象和人工复核情况，不能直接报准确率。

### 56. 已经做过真实流量实验吗？结果能说明什么？

回答：已在当前电脑完成 60 秒被动观测，采集到 2,146 个 IP 包，形成 62 条流，全部完成推理，模型均预测为 BENIGN，规则未命中。再次重放时，逐流特征、完整模型概率和规则结果一致。这证明本次实际流量走通了采集、特征提取和推理流程，但没有独立标签，因此没有计算准确率、误报率或攻击召回率。

项目还补充了独立会话目录、全部流记录、人工标签模板和评分工具。复核标签后可比较模型、规则和组合方案；当前仍需跨业务场景、多轮且带攻击标签的验证。详见[本机真实流量观测记录](./real_traffic_observation.md)和[评估指南](../docs/real_traffic_evaluation.md)。

## 十一、简短背诵版

### 项目一句话

本项目基于 CICIDS2017 构建了一个网络入侵检测与安全运营原型系统，实现了从数据清洗、模型训练对比到实时流量检测、告警展示和 SHAP 可解释分析的完整闭环。

### 技术路线一句话

离线训练阶段对比 RandomForest、XGBoost、CNN-LSTM 和 Transformer，最终选择更适合表格流量特征的 XGBoost；在线检测阶段通过 FastAPI 接入模拟流量、pcap 回放和 Scapy 实时抓包，并在 Vue 控制台中展示告警。

### 创新点一句话

项目的特色是将单流模型与跨流规则结合，把 SHAP 解释接入告警复核，并提供模拟、回放和实机采集的分层验证入口，形成可运行的工程原型。

### 不足一句话

当前系统仍是原型，主要不足是数据集较旧、实时特征提取与 CICFlowMeter 存在近似差异、深度学习模型未充分调优、少数类样本极少，以及生产级权限、性能和模型更新机制还不完善。

### 改进一句话

后续会从全量数据和真实流量验证、特征提取对齐、深度模型调参、阈值校准、低误报告警策略和生产级存储权限体系几个方向继续完善。
